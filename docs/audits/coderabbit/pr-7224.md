## Finding 1: Duplicate shutdown cleanup after signal handling

Comment: https://github.com/Neko-Catpital-Labs/Invoker/pull/7224#discussion_r3707130086

Quoted finding:

> Guard the normal quit cleanup when the signal handler already owns shutdown.
>
> For `owner-serve`, `runHeadless(cliArgs, headlessDeps)` blocks while `headlessOwnerServe` polls, so a SIGTERM/SIGINT can start signal cleanup asynchronously. The `finally` block then enters `runHeadlessShutdownCleanup` regardless, so it can call `persistence.requeueRunningWorkflowMutationIntents()`, `persistence.close()`, `writerLock.release()`, and `messageBus.disconnect()` a second time. Guard the final cleanup and `process.exit(exitCode)` so only the first shutdown path runs cleanup.

Severity: Major

Verdict: invalid

Evidence:

On current master, `packages/app/src/main.ts:1065` defines `headlessSignalShutdownInProgress`. The signal handler returns immediately if the flag is already set at `packages/app/src/main.ts:1068`, sets it before starting signal cleanup at `packages/app/src/main.ts:1069`, runs `runHeadlessShutdownCleanup(...)` at `packages/app/src/main.ts:1071`, and exits from the signal-owned path at `packages/app/src/main.ts:1080`.

The normal `finally` path is now guarded: `packages/app/src/main.ts:2037` checks `if (!headlessSignalShutdownInProgress)`, `packages/app/src/main.ts:2038` sets the flag before cleanup, `packages/app/src/main.ts:2039` runs normal shutdown cleanup only inside that guard, and `packages/app/src/main.ts:2040` calls `process.exit(exitCode)` only inside the guarded block. Because signal cleanup sets the flag first, the normal `finally` path skips both cleanup and normal exit after signal shutdown begins. The duplicate-cleanup problem flagged by CodeRabbit no longer exists on current master.
