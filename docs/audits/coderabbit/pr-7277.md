## Finding 1: prune scoped remote-tracking refs

Source: <https://github.com/Neko-Catpital-Labs/Invoker/pull/7277#discussion_r3708273827>

Quoted finding:

> "Prune scoped remote-tracking refs before matching them."

Severity: Major

Verdict: valid

Evidence:

Current master no longer contains the PR helper `fetchStackHeadsPrefix`, but the same stale remote-tracking ref risk remains in the replacement publication guard. In `scripts/create-pr.mjs`, `assertPublishedMergifyBranch` accepts `getCurrentUpstream()` as `publishedRef` at line 775, or falls back to the local remote-tracking ref `origin/${branch}` when `git rev-parse --verify` finds it at lines 776-778. The guard then treats the branch as published when ``revList(`${publishedRef}..HEAD`)`` is empty at lines 790-791.

Those checks use local refs only. There is no fetch or prune in `assertPublishedMergifyBranch` before trusting `origin/${branch}`, so a stale `origin/stack/...` ref that still points at `HEAD` can still make the update pass even if the real remote branch was deleted.

## Finding 2: make Change-Id fallback valid through publication check

Source: <https://github.com/Neko-Catpital-Labs/Invoker/pull/7277#discussion_r3708273837>

Quoted finding:

> "Make the Change-Id fallback valid through the publication check."

Severity: Major

Verdict: valid

Evidence:

Current master no longer contains the PR helper `findMergifyPublishedRef`, but the publication guard still has no path that treats a unique same-`Change-Id` remote tip as published when its SHA differs from local `HEAD`. `scripts/create-pr.mjs` uses `Change-Id` only to classify a branch as Mergify-managed in `branchHasChangeId` at lines 737-741. The later publication check in `assertPublishedMergifyBranch` selects only the current upstream or `origin/${branch}` at lines 775-778, then accepts only when the SHA ancestry range ``revList(`${publishedRef}..HEAD`)`` is empty at lines 790-791.

That means a remote tip with the same `Change-Id` but a different SHA is still rejected as an unpublished local commit, because current master performs no `Change-Id` equivalence check before the SHA-based `revList` gate.
