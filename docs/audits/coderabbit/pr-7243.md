## Finding 1: Cross-runner expired lease release

Comment: https://github.com/Neko-Catpital-Labs/Invoker/pull/7243#discussion_r3710929591

Quoted finding:

> When two writable `TaskRunner` instances share the same data store, runner B sees runner A's expired-but-active lease as a foreign orphan. `releaseExecutionResourceLease` deletes by `(resource_key, holder_id)` and can free runner A's lease while it is still executing.

Severity: Major

Verdict: invalid

Evidence:

- The flagged code still exists on master: `packages/app/src/launch-dispatcher.ts:187` starts `sweepExpiredResourceLeases`; `packages/app/src/launch-dispatcher.ts:205` compares lease metadata `runnerInstanceId` to the current runner; `packages/app/src/launch-dispatcher.ts:206` checks `hasActiveExecutionForLeaseHolder`; `packages/app/src/launch-dispatcher.ts:208` renews same-owner live leases; `packages/app/src/launch-dispatcher.ts:211` releases expired leases that are not same-owner live leases.
- The delete primitive does delete by `(resource_key, holder_id)`: `packages/data-store/src/sqlite-adapter.ts:3441` defines `releaseExecutionResourceLease`, and `packages/data-store/src/sqlite-adapter.ts:3443` executes `DELETE FROM execution_resource_leases WHERE resource_key = ? AND holder_id = ?`.
- The premise required for the bug is not a supported current-master topology. `docs/persistence-architecture-single-writer.md:9` states that exactly one process owns writable database access and all other processes delegate mutations or open read-only. The owner-boundary contract at `docs/persistence-architecture-single-writer.md:23` identifies the owner process, and `docs/persistence-architecture-single-writer.md:26` says non-owner processes cannot initialize writable persistence.
- Current source enforces that boundary. `packages/app/src/main.ts:761` acquires the DB writer lock before writable initialization; `packages/app/src/db-writer-lock.ts:230` throws when another live holder owns the lock. `packages/app/src/viewer-db-boundary.ts:30` passes `ownerCapability: !options.readOnly` into `SQLiteAdapter.create`, and `packages/data-store/src/sqlite-adapter.ts:772` through `packages/data-store/src/sqlite-adapter.ts:778` reject writable file-backed initialization without owner capability.
- Headless mutating commands try owner delegation first rather than opening another writable runner: `packages/app/src/main.ts:948` through `packages/app/src/main.ts:969` delegate mutating headless commands, and `packages/app/src/main.ts:981` through `packages/app/src/main.ts:989` fail non-standalone mutations when delegation does not succeed. Standalone writable mode is explicit (`packages/app/src/main.ts:933`) and initializes through the same `initServices` path (`packages/app/src/main.ts:1088` through `packages/app/src/main.ts:1092`), which acquires the writer lock.
- Existing tests cover the intended lease-liveness behavior in the supported topology. `packages/app/src/__tests__/launch-dispatcher.test.ts:1242` through `packages/app/src/__tests__/launch-dispatcher.test.ts:1300` verifies that a same-runner active expired lease is healed, while same-runner inactive and different-owner expired leases are released. `packages/data-store/src/__tests__/owner-boundary.test.ts:37` through `packages/data-store/src/__tests__/owner-boundary.test.ts:47` verifies writable initialization without owner capability is rejected, and `packages/app/src/__tests__/writer-lock-default.test.ts:66` through `packages/app/src/__tests__/writer-lock-default.test.ts:70` verifies a second writer-lock acquisition is blocked while the first is held.

The finding correctly describes what would happen in an unsupported multi-writer setup, but it is invalid against current master because the claimed "two writable `TaskRunner` instances share the same data store" topology is blocked by the owner-boundary and writer-lock design.
