Why the PRs are so different

  1. The prompts were shared, but several acceptance terms were ambiguous. Each model chose different API shapes, defaults, schemas, and error behavior.
  2. The PRs are cumulative. Feature 03 builds on each model's own feature 02, so early contract differences become larger integration differences in later PRs.
  3. Each model wrote tests for its own interpretation. Green local tests therefore prove internal consistency, not cross-model equivalence.
  4. The mechanical precheck ran install and test commands, but it did not exercise every named script or real CLI, Postgres, Chrome, Slack, and concurrent-worker boundary.
  5. Implementation depth varied materially: Claude generally built broader guards and tests, Codex preferred narrower slices, and Qwen often used shallow mocks or committed generated agent artifacts.

Why Qwen PRs #25 and #26 fail

PRs #25 and #26 both fail at their own heads. They fail the same encrypted-persistence assertion, but #26 also has independent lifecycle defects.

PR #25 — encrypted persistence

  • The immediate red test is an object-aliasing bug in the database double. The mock returns its stored row object by reference; getRewriteRun deletes ciphertext_payload from that object after decrypting it, so the mock's stored ciphertext disappears.
  • A real pg query normally returns a fresh row object, which is why PR #27's later clone-the-row repair is a legitimate test-double fix. It does not retroactively make PR #25 green.
  • PR #25 also has production-quality gaps: unreadable ciphertext can be omitted instead of raising a hard error, raw identifying audit values can be stored under a redacted name, and encryption-key handling truncates long strings instead of decoding an exact 32-byte key.

PR #26 — durable lifecycle

  • PR #26 inherits the same red persistence test and edits the fixture without fixing the by-reference deletion mechanism.
  • Its lifecycle claim is a read followed by an unconditional update, so two workers can claim and bill the same run.
  • Provider failures do not retry as specified; reclaim resets attempts to zero, making repeated reclaim cycles unbounded.
  • TTL cleanup ignores the persisted expiry contract and excludes pending or processing rows, so live encrypted text can survive indefinitely.
  • Its mocks JSON-parse payloads while the inherited production persistence returns strings, hiding that the real provider path can receive undefined text and lose persona policy.
  • Invalid provider output is encrypted and written over the original request instead of failing closed without persisting untrusted output.

Narrowest practical slices for equivalent results

Smaller prompts alone will not produce equivalent systems. Each model must start from the same frozen parent and pass the same black-box conformance command before its lineage advances.

Confirmed safety invariant: For every slice: start all models from the same frozen parent; define exactly one externally observable behavior with one shared golden command; preserve every prior golden command; reject implementation-specific substitutes; do not advance a lineage until it passes.
